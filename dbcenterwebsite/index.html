What it is

The actual postgres binary, started by your program.

Not an emulation and not a fork. DBCenter downloads PostgreSQL once, runs it as a child process against a data directory, and stops it with your program. Every SQL feature works, because it is PostgreSQL.

For AI agents

SQL without handing over your data

read_only=True runs a statement in a read-only transaction that is rolled back. PostgreSQL refuses the write, however the SQL is phrased. An MCP server ships with it.

For AI agents

Read-only is enforced by PostgreSQL, not by a filter.

Most read-only database tools check the SQL text, and the text can hide a write. DBCenter never inspects the SQL, so there is nothing to slip past.

  • Refused, however it is phrased: a DELETE inside a CTE, nextval(), DDL. The test suite tries the usual bypasses.
  • An MCP server for Claude, Cursor or any MCP client. Read-only unless you pass --allow-writes.
  • Memory with pgvector, one call away: a table with a vector column, queried by distance.
agent.py
db.query("SELECT sum(total) FROM orders", read_only=True)  # fine

db.query("WITH gone AS (DELETE FROM orders RETURNING *) "
         "SELECT count(*) FROM gone", read_only=True)
# Error: cannot execute SELECT in a read-only transaction
# and every order is still there

In tests

Test against PostgreSQL, not something like it.

SQLite in tests misses what production PostgreSQL does, and testcontainers needs Docker on every machine and in CI. Here the fixture is there as soon as the package is installed.

  • One server per test session, so the cost of starting PostgreSQL is paid once.
  • An empty public schema for every test, so tests cannot see each other's tables.
  • Your own driver too: postgres_dsn for psycopg, postgres_url for SQLAlchemy.
test_orders.py
def test_orders(dbcenter_db):
    dbcenter_db.query("CREATE TABLE orders (id serial, total numeric)")
    dbcenter_db.query("INSERT INTO orders (total) VALUES (10)")
    rows = dbcenter_db.query("SELECT count(*) AS n FROM orders")
    assert rows[0]["n"] == 1

Your data in your own bucket

Lose the machine, keep the data.

With multi_user_sync=True each table remembers what changed since its last sync and ships just that to S3, Cloudflare R2, Tigris or MinIO, as Parquet with one column per field.

  • Rebuild anywhere: another machine, or this one after losing its disk, restores from the bucket.
  • Several writers can share one bucket. The newest edit wins and the losing version is kept, not dropped.
  • Analytics from the same files: with columnar=True, aggregates read the Parquet through DuckDB, 4.5x to 8.7x faster than PostgreSQL on one core.
sync.py
bucket = dbcenter.S3StorageAdapter(
    "my-bucket",
    endpoint="https://<account>.r2.cloudflarestorage.com",
    access_key="...", secret_key="...",
)

laptop = dbcenter.DBCenter(path="./laptop", multi_user_sync=True)
laptop.collection("notes").insert_one({"body": "remember the milk"})
dbcenter.SyncEngine(laptop, bucket).sync_table("notes", 10_000)

# on another machine
server = dbcenter.DBCenter(path="./server", multi_user_sync=True)
dbcenter.SyncEngine(server, bucket).pull_and_apply("notes")

Alternatives

How it compares.

SQLite (+ Litestream)

Lighter and simpler. But it is not PostgreSQL: no pgvector, no PostGIS, and different SQL from the database you deploy.

testcontainers / Docker

Real PostgreSQL too, but it needs Docker on every laptop and CI runner, and it does not run in Colab.

pgserver, postgresql-wheel

The same idea, in Python. Neither has been updated since 2024 and 2021, and they stop at PostgreSQL 16 and 14.

PGlite

PostgreSQL compiled to WASM, for JavaScript. A single connection, and in the browser rather than in Python.
